# Orbit 0.1.1

Orbit 0.1.1 修复 dedicated server 初始化，并把 Fabric、Quilt、Forge 与 NeoForge
服务器安装统一接入严格的平台快照流程。客户端、启动器实例和服务器现在都向 Orbit
的其余部分提供同一种已验证运行时模型。

## 安装包

- **Windows x64**：`orbit-0.1.1-x86_64.msi`
- **Debian/Ubuntu amd64**：`orbit_0.1.1-1_amd64.deb`
- **完整性校验**：下载 `SHA256SUMS` 后执行
  `sha256sum --check SHA256SUMS`

Windows MSI 支持安装目录、系统 PATH、维护/修复，以及卸载时选择是否删除默认
AppData。MSI 尚未签名，Windows 可能显示未知发布者提示。

## Dedicated server 修复

- 修复含 `eula.txt` / `server.properties` 和 Mojang `versions/` 的服务器目录被误判为
  客户端共享游戏根，继而无法确认已安装 Fabric Loader 的问题。
- Fabric 读取官方 server bootstrap 的 `install.properties`、生成 launch JAR 的
  manifest classpath，以及 Mojang bundler 的 `META-INF/versions.list` /
  `META-INF/libraries.list`。
- Quilt 读取 `quilt-server-launch.jar` 的实际 classpath 和
  `quilt-server-launcher.properties`。
- 当前 Forge 读取根目录 bootstrap shim 与 `bootstrap-shim.list`；旧版
  ModLauncher Forge 和 NeoForge 读取安装器生成的当前平台 `unix_args.txt` /
  `win_args.txt`。
- Forge shim、Mojang bundler 引用的文件会按清单 SHA-256/SHA-1 校验；路径必须仍在
  当前实例目录内。

四种 Loader 最终都只向核心返回 Minecraft 版本、Loader/version、实际 Minecraft
JAR、Loader JAR 和完整 runtime classpath。`init` 与 `sync` 共用该结果，之后的命令
仍只读取 `orbit.toml` 中固定路径与哈希。

## 严格行为

- Orbit 不执行 `launch.sh`、`run.sh`、`run.bat` 或用户 wrapper，也不从文件名或进程
  猜测启动配置。
- 服务器安装缺少实际 JAR、清单 hash 不匹配、版本声明不一致，或同一目录存在多个不同
  runtime 时直接报错。
- 仅有服务器 marker、但没有由 Fabric、Quilt、Forge 或 NeoForge 官方安装器生成的
  完整本地运行时，不再退回交互式 Loader 猜测。
- `sync` 会重新读取本地安装规格并刷新平台快照；它仍不联网。

## 升级说明

0.1.1 不修改 `orbit.toml` / `orbit.lock` schema。现有 0.1.0 项目可直接升级；在
dedicated server 中运行一次 `orbit sync`，即可把实际服务器 runtime 路径与哈希写回
平台快照。

CurseForge 仍要求显式配置用户自己的 API Key；Windows 只发布 x64 MSI，deb 只发布
amd64。完整命令与设计契约见仓库 `README.md` 和 `docs/`。
